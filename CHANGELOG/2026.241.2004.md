# 2026.241.2004 — feat: install the sway stack on Arch/CachyOS too

## Summary

`pod-sway` was **Fedora-only**. The whole package list lived under `distro.fedora`, so
composing this candy on an Arch or CachyOS base installed nothing at all — the cascade
matched no section, the compositor was simply absent, and the failure surfaced only at
runtime as a missing binary.

Adds the matching `arch:` section. It also covers CachyOS: that base declares
`distro: [cachyos, arch]`, so the cascade resolves the same section on both.

Package mapping from the existing Fedora list, each verified to resolve on the CachyOS
base before being written:

| Fedora | Arch | why |
|---|---|---|
| `xorg-x11-server-Xwayland` | `xorg-xwayland` | straight rename |
| `mesa-dri-drivers` | `mesa` | Arch ships the DRI drivers inside `mesa` |
| `mesa-vulkan-drivers` | `vulkan-swrast` | Arch splits Vulkan per vendor; the software rasteriser is the one that works on a headless, GPU-less bed. A GPU consumer composes its own `vulkan-radeon` / `vulkan-intel` / nvidia stack. |
| `libglvnd-egl` + `libglvnd-gles` | `libglvnd` | one package on Arch |
| `sway`, `fuzzel`, `egl-wayland`, `wlr-randr` | same | identical names |

**Nothing else changes.** The `setcap: /usr/bin/sway` step, the `sway-wrapper`, the config
and every `check:` step were already distro-neutral, and the `fedora:` section is untouched
— so this is purely additive for existing consumers. The `require:` on `pod-dbus` already
resolves on Arch (that candy carries `distro.arch`).

The candy's `description:` said the stack installs "on Fedora", which this change makes
untrue, so it is updated in the same commit rather than left as a stale claim.

### Why now

Landing punktfunk streaming-host support on Arch/CachyOS
([`layer-punktfunk`](https://github.com/opencharly/layer-punktfunk),
[`plugin-punktfunk`](https://github.com/opencharly/plugin-punktfunk)) needs a wlroots
compositor with a live sway IPC socket: punktfunk creates its virtual output by calling
`swaymsg create_output`. `pod-sway` is the org's sway candy, and duplicating it into a
second Arch-only candy would be exactly the R3 duplication the rulebook warns about — so
the correct fix is to make the existing one work on Arch.
